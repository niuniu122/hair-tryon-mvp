# 咨询范围与输入

- 用户输入：带标注的桌面参考图，明确要求左侧为摄像头/冻结用户脸、右侧为最终发型预览、底部为可选发型。
- 路由角色：Product Manager 与 Frontend Developer。
- 选择原因：确认新呈现是否改变已批准流程，并判断能否复用现有 API 快速实现。
- 设计方法：使用用户截图作为信息架构参考，并以产品工具设计规则检查状态、可访问性和加载反馈；不复制参考品牌。
- 预期输出：最小 PRD 修订、验收标准、预计修改范围和阻塞判断。

# Product Manager 结论

本次不构成核心产品范围变化，只把已有能力收进“双预览 + 底部发型轨道”：

- 左侧同一舞台依次采集并切换正面、固定右侧面。
- 右侧同一舞台切换正面、右侧面、背面三个独立结果状态。
- 查看背面时不伪造背面原图，左侧保留最近输入并明确“本次未采集背面”。
- 顶部保留参与者编号、同意状态、模型和结束运行；底部只保留五款发型与主动作。
- 两次采集、三视图调度、模型锁定、幂等、失败保留和内部验证边界都不改变。

# Frontend Developer 可行性结论

- 现有 API 和响应结构已经支持两份输入、三个结果、部分成功、错误/重试、模型锁定与结束清理，无需修改后端或数据结构。
- 预计只修改 `static/index.html`、`static/styles.css`、`static/app.js`、`static/ui-state.mjs` 和 `tests/ui-state.test.mjs`。
- 新增的前端本地状态仅为活动输入标签、活动结果标签、用户是否手动切换结果和媒体舞台派生状态。
- 动态主按钮按流程承担开始、摄像头、冻结正面、冻结右侧面和生成三视图；这是当前快速 MVP 的推荐默认，不需要再向用户暴露实现选择。

# 关键体验与验证结论

- 双舞台同尺寸，不出现第三个主预览区，也不再并列三张结果卡。
- 生成状态按视图限制在右侧舞台内，不能用全局遮罩覆盖已成功结果；加载同时显示骨架/进度文字。
- 仅在用户尚未手动选择结果标签时，首个成功结果可以自动切换。
- 标签采用标准 tab 语义、可键盘操作并有可见焦点；桌面浏览器 200% 缩放仍能访问关键操作。

# 冲突与处理

参考图只展示一个输入舞台和一个结果舞台，而原 PRD 需要两次采集和三视图。处理方式是用标签在同一舞台内切换，不减少能力、不增加背面输入，也不改变 API。旧开发授权不覆盖新的可见信息架构，因此进入 `prd_revision` 并等待 v1.5.0 明确批准。

# 阻塞判断

没有产品或技术阻塞项。v1.5.0 获明确批准后可直接进入前端 TDD 实施。
